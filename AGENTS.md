# Working in Nyx

## Authority and task flow

The user authorizes development and modification of the Nyx library and Nyx
Studio, including existing base classes, specialized interfaces, public APIs,
adapters, shared infrastructure, generators, tests, documentation and necessary
prerequisites. These are editable development sources. Changing a library file
or contract does not require renewed approval. Update affected consumers and
perform appropriate compatibility and target checks as part of the change.

Implement reusable capabilities in the library and its target adapters. Earlier
file lists do not confine implementation to Studio, tests or helper units, and
must not force a workaround when the correct fix belongs in the library.

Assignments, source inventories, review records and planned scopes coordinate
work; they do not make files immutable or establish permission allowlists. Root
may adjust ownership and include necessary prerequisite files directly. A short
validation freeze lasts only while actual readers need that source snapshot;
it does not prevent changing the library after those readers finish.

Earlier file-scope restrictions and approval gates are superseded. Historical
receipts document past work, not restrictions on new work. Do not recreate such
gates in instructions, task records or private handoff state, or request
file-by-file permission for this authorized development.

Start with [PROJECT.md](PROJECT.md), the current task in [TODO](TODO/README.md)
and the current entry in [WORK.md](WORK.md). Apply [TASKFLOW.MD](TASKFLOW.MD) and
Athena's [task-flow standard](athena/docs/task-flow.md): follow prerequisites,
preserve acceptance criteria, record discovered gaps and move tasks to
`TODO/DONE/` only with accepted evidence. Plans do not add approval boundaries.

Keep this file for durable project guidance. Put current assignments, progress,
source identities, failures and remaining checks in WORK.md or the relevant task,
not an ever-growing instruction journal. The current work entry supersedes
historical handoffs without erasing their evidence.

## Collaboration and validation

- Scooty coordinates implementation and the existing Lil' Scooty helper. Keep
  their edits disjoint, give the helper a useful next prerequisite and resolve
  ownership changes directly between agents. Do not add further agents unless
  the user requests them.
- Coordinate compiler and runtime readers against a stable source snapshot.
  Pause edits to the sources being read, join actual running jobs and then
  resume implementation. Source review and these short freezes serve correctness;
  they do not require another user approval.
- Run checks appropriate to the changes. Existing authorization for the same
  local regression and necessary reruns persists. Do not convert ordinary builds,
  read-only source inspection or reversible local testing into permission loops.
  Respect actual external-action boundaries and explicit user constraints.
- Preserve unrelated work. Inspect the checkout and toolchain before changing
  setup; do not reinstall working compilers or edit dependency sources in place.
- Preserve useful regression assertions and failure evidence. Distinguish source
  review, successful compilation, executed behavior, visual inspection and full
  acceptance. A compile alone does not prove interaction, accessibility, visual
  quality or browser/LCL parity. Do not assign completion credit from work volume.
- Use existing backlog tasks and their prerequisites. Avoid recurring cleanup,
  equivalent planning variants or additional reports that do not advance the
  requested product. Report a blocker only when a real missing input or external
  condition prevents meaningful progress.

## Product and architecture

- Implement product code, generators, servers, build tools and substantive test
  tools in Pascal using `{$mode delphi}`. Shell scripts may orchestrate platform
  tools. Do not add Node, npm, Python or JavaScript frameworks to Nyx. JavaScript
  generated by pas2js is a build artifact.
- Target FPC with Lazarus Component Library and pas2js browsers through one
  portable contract. Keep DOM/LCL types behind adapters and exercise shared
  behavior on both targets.
- Preserve explicit ownership and reference-counted specialized interfaces.
  Documents own pages and reusable components; nodes own descendants; renderers
  and views must not create reference cycles back into the tree. Document borrowed
  objects, retirement, cancellation and callback lifetimes beside their code.
- Use strong Pascal types in built-in authoring and generated code: enums for
  closed choices, Boolean/numeric values, distinct references for open names and
  fluent configuration objects. Raw property strings belong at explicit
  persistence/extension boundaries. Generated code should feel crafted, with
  purpose/control names, specialized interfaces and readable blocks.
- Preserve atomic state admission, exact Unicode/numeric values, token lifetimes
  and target wire/generation behavior. Runtime applications use independent state
  stores. Store-only fixtures do not establish live-binding integration.
- Compound and advanced controls are first-class requirements. Compose reusable
  parts, named slots, typed state/events and shared recipes while preserving
  independent ownership and extensibility.
- Nyx Studio must be built with Nyx. Put reusable designer/editor controls in
  the library and target adapters; Studio consumes public Nyx contracts.
- Use Studio's semantic MCP tools as the primary way to inspect, compose and
  modify demos and active designs. Query bounded context, preserve user work,
  supply expected revisions and group related edits into undoable transactions.
  Use rendered previews selectively. Browser/LCL input harnesses still qualify
  behavior that document operations cannot prove. Record missing semantic tools.
- Output targets are optional and can be selected/configured at any time in
  Studio. A missing application compiler must not block a built Studio or design
  work. Keep machine compiler paths separate from exported designs.
- Keep editor defaults free of branch names and development milestones. Use
  English for starter documents and demos while preserving full Unicode support
  and user-authored content.

## Coding style

Apply Athena's [coding standards](athena/docs/coding-standards.md),
[browser cautions](athena/docs/platforms/browser.md) and
[validation matrix](athena/docs/validation.md), together with existing Nyx style.

- Preserve thoroughly commented code. Explain public contracts, properties,
  ownership/lifetimes, failure behavior and non-obvious implementation choices.
- Give every added or changed type declaration its own immediately preceding
  purpose comment, including private types, forwards, aliases, enums, records,
  interfaces, callback types, generic helpers and external bridges. Explain the
  relevant constraints instead of restating the name. Bridge comments identify
  the platform API, borrowed host objects and availability limits. A comment for
  the entire type block does not replace comments on its declarations.
- Leave a blank line above each `if` block. Use two-space indentation and expanded
  `begin`/`end` bodies, with one field or local declaration per line.
- Declare `{$codepage utf8}` in owned Pascal units/programs. Use `TNyxText` for
  portable text, `TNyxStrings` for owned user-text collections and byte streams
  at file/HTTP boundaries. A source directive alone does not protect native ANSI
  concatenation or RTL collections. Test supplementary Unicode through storage,
  history, generated compilation and controls; avoid global codepage changes.
- Preserve the MIT license and existing `mr-highball` attribution. Keep private
  paths, accounts, hosts and personal configuration out of committed files.
