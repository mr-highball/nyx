# NS-3_data-toolbar_02 — Coordinate a toolbar with a collection query

[North stars](../MILESTONES.md) · [Task catalog](README.md) · [Task flow](../TASKFLOW.MD)

**Description:**

Make a public opt-in DataToolbar perform real search, sort and Clear on an
existing List/Table collection view in an ordinary application. This is the
runtime/API deliverable beneath [Studio DataToolbar authoring](NS-3_data-toolbar_01.md).
The parent retains authored intent, paired history, Save/Open and exact generated
application acceptance.

North star: NS-3, original components criteria1/3; no extra completion credit.
The static toolbar recipe, semantic actions and INyxCollectionView.ConfigureQuery
already exist. Static faces alone do not qualify this task.

**Current priority — 2026-10-26:**

After the native table and two Studio workspace checkpoints, this is the next
user-facing outcome in the ranked queue. Root works solo. Follow the unchanged
coordinator01 → parity01 → renderer prerequisites first, reusing applicable
accepted evidence and addressing actual remaining interaction requirements.
This does not accept the coordinator parent or waive target quality. Existing
file/release wording below coordinates historical work, not source permission.
No new resolver, static toolbar recipe or query-policy variant is the deliverable.
The finish line remains real Search, Sort and Clear, then ordinary Studio and
the exact saved/generated application under authoring01.

Resolve two concrete seams before coding Q1. The current static recipe exposes
search/sort/create/refresh, so opt-in configuration needs an admitted named Clear
action while preserving the default recipe/GUID. Reset visible Search and typed
Sort through their existing scalar input/binding owner; projection Text changes
captions, not input values. Specify ownership of intervening target/query changes
so Clear/disposal never restore an obsolete baseline. Use ConfigureQuery and the
existing state/selection/event owners; no replacement engine follows.

The read-only owner review narrows that reset gap: live input admits through
LiveBindings and State.Apply, while an INyxTextInput.Value setter only configures
its node. A future scoped scalar command must reuse the existing live owner,
exact accepted roles/generation and copied typed values without exposing a Node
or controller. Admit Search and Sort together; two unrelated sequential writes
cannot promise one Clear operation. Existing caller bindings/read-only/domain
rules still apply. Specify validation/publication across scalar reset and query
change before source release rather than assuming those owners commit together.

Capture the admitted baseline and the canonical session observation for each
command. Before mutation, verify the exact view/store/source, mounted generation,
session intent and own live lease. Peer changes require a fresh capture and
preservation of their current contributions. Actual raw query/target replacement
must refuse or retire former authority, never be overwritten by Clear; equal raw
assignments remain no-op. Query notification failure remains committed. The
opt-in ordinary Clear button uses the existing Clear semantic; compatible custom
parts/captions/callbacks survive, and an occupied incompatible role refuses the
whole candidate. The static four existing accessors/GUID remain unchanged.

Read-only design can advance while prerequisites are pending. Acceptance remains
downstream of the complete coordinator task, including05's actual-browser gate;
this packet list does not bypass that dependency or authorize a host rollout.

The shared ownership rule is now specified with
[column filtering02](DONE/NS-3_control-usefulness_02.md): one view-owned baseline and
independent owner/channel predicates, plus one visible shared user-sort vector.
CurrentQuery is the baseline on first admission; later surfaces join it. Clear
withdraws this toolbar's search and resets sorting only while it owns that vector.
In isolation this restores the exact admitted baseline; with peers it preserves
their current contributions. Separate explicit global resets remove all user
filters/reset order. Same-origin reacquisition gets a fresh exact owner token,
never another attachment's authority. Actual raw query replacement revokes the
former session generation; equal replacement remains a no-op. The existing
prepared state/query owner admits visible Search/Sort reset together. This settles
the design seam only: Q1 implementation remains blocked by its unchanged parent,
and all five original acceptance criteria below remain required.

**Pull checklist — Q1:**

Status: blocked for implementation by complete common coordinator integration.
The existing owner review may proceed read-only while the prerequisite chain is
followed. Necessary source changes are authorized; there is no file-release
approval gate. Deliver useful input/query behavior, not a new static recipe.

- Settle the cross-owner publication contract before source release: typed Search
  and Sort resets plus the query change admit together or all refuse. Validation,
  cancellation or stale input before publication changes none of them. A failure
  in notification after publication is reported as committed; never claim rollback
  after a visible value/query has committed.
- Specify simultaneous attachment to the same target: deterministic refusal,
  composition or retirement must have an explicit public rule. Last-owned-query
  checks alone do not establish that rule. No attachment may overwrite another
  toolbar's accepted query or restore its obsolete baseline.
- Implement real typing, typed Sort and visible Clear through existing live
  scalar/state and collection-query owners. Admit the required Clear role with
  the whole candidate; preserve static absence, Disabled, GUID/default recipe,
  custom parts, captions and caller callback policies.
- Preserve rows/defaults, authored query composition, hidden selection and each
  attachment's exact scope/generation. Missing/incompatible roles, ownership loss
  and stale commands refuse before mutation; late work cannot revive a retired
  attachment. A focused public consumer must exercise those observable outcomes.

**Pull checklist — Q2:**

Status: follows Q1. One ordinary application uses two independently owned
toolbars, with actual input and copied data through the public contract.

- Type searches, change Sort, produce empty results and Clear back to the exact

- Exercise both different targets and the documented same-target rule. Replace

- Replace/navigate/dispose one instance, then use the peer's real controls.
  Former commands must refuse. Native execution has clean heaps and matching

**Acceptance Criteria:**

- Copied typed options identify a scoped List/Table and schema-checked search/
  sort fields, comparison and order. Missing, foreign, ambiguous or incompatible
  targets refuse before query changes. Static absence and explicit Disabled
  preserve current behavior; configuring does not rewrite caller event policies.
- Real control input changes displayed membership/order through ConfigureQuery.
  Search composes with the admitted authored query; an accessible visible Clear
  restores that exact baseline. Empty results, repeated searches and sort changes
  are useful results, not just updated configuration metadata.
- Preserve data rows, defaults, paging/typeahead ownership and hidden selection
  membership. Define ownership when the target/query changes while attached;
  simultaneous toolbar attachment follows a documented deterministic rule.
  Clear or disposal must never blindly restore an obsolete baseline or overwrite
  another toolbar's accepted query.
- Use the common prepared coordinator path and accepted event generation.
  Cancellation, stale input, replacement and independent reusable instances
  cannot mutate a foreign or retired view. Refusal is unchanged; observer failure
  after publication remains committed.
- Execute a public application consumer with independent instances, typing,
  sort, Clear, empty results and lifecycle/refusal cases on native with clean
  heaps. Compile matching browser assertions. Document caller use and static
  compatibility; Studio/save/generated integration remains explicitly open.
