# NS-4_interact-flows_02 — Prepare root routes for a future event view

[North stars](../../MILESTONES.md) · [Task catalog](../README.md) · [Task flow](../../TASKFLOW.MD)

**Description:**

Deliver a public managed route-preparation API that an ordinary host can use
before its first view is accepted. Existing replacement routing needs a former
binding; immediate binding observes the current generation. Neither supplies
dormant root routes for the renderer's prospective view.

of [working Interact flows](../NS-4_interact-flows_01.md). Credit stays with the
original outcome; this split earns none. Starting owners are
[flow routing](../../src/nyx.flow.routing.pas), prepared event observations and
[the maintained route consumer](../../tests/nyx_flow_routes_tests.lpr).

**Acceptance Criteria:**

- A caller prepares complete root routes from the exact already-realized
  candidate and document. Runtime IDs are collected once; there is no second
  realization, live subscription or requirement for a former binding.
- Reuse the existing route plans, resolver and supplied prospective event view.
  State precisely which router/context/generation relationships are checked and
  which require caller pairing. An interface without ownership evidence cannot
  justify an invented identity check. Executable creators are not resolved while
  preparing; metadata supplies no additional host authority.
- Complete admission and outward validation precede final local readiness
  checks. Routes stay dormant until pure ownership/flag installation; observations
  activate with the accepted event view. A refusal or abandoned preparation
  retires only its reservations and leaves the former live routes usable.
- The installed binding survives preparation retirement, dispatches exactly
  once through the ordinary router and cancels late work on disposal. Copied
  Details and scalar Value, route order, resolver reports and old manual and
  replacement APIs retain their contracts and interface identities.
- Execute a maintained native host consumer for first publication, replacement,
  abandonment, cancellation, stale/reentrant validation and postcommit failure,
  with clean heaps. Compile the matching browser consumer while retaining its
  behavioral assertions; compilation alone does not establish browser execution.

Studio adoption and the saved/generated journey remain downstream acceptance
in the parent task, separate from this independently usable host API.

Contract decision, 2026-10-21: the caller pairs the prepared view with its router;
current interfaces expose no cross-owner identity. Preparation and Validate
require an active context with the router's exact scheduler and the view's exact
prospective generation. Final readiness reads only the retained future token
and event-view fence. The host must keep that staged context stable and cancel
its future generation, or fail its own local readiness fence, before retiring or
changing it. Generic context Close alone does not cancel a generation. No new
event/context GUID or ownership claim is introduced for this API.

**Blockers**

- None. Existing event-view, publication and application-context owners supply
  the foundations. Resolve their authority contract before implementing guards.
